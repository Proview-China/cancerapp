## Context

认证和会话由已归档的 `add-user-authentication-sessions` 提供。`backend/src/routes/cases.ts` 中病例列表、详情、创建、删除、样本、文字报告、排序和组织切片分析汇总当前没有统一病例授权；创建病例的 `INSERT ... ON CONFLICT(identifier) DO UPDATE` 会更新已存在病例。前端 `caseService.ts` 直接调用这些接口，部分 GET/DELETE/上传请求当前没有复用认证服务的 credentials/CSRF 处理。

## Goals / Non-Goals

- Goals: 在后端对所有临床病例 API 作 fail-closed 授权；保留管理员、病理医生、研究人员三角色边界；显式迁移旧病例 owner；兼容合法所有者和受授权用户的现有病例流程。
- Non-Goals: 所有权转交、删除审批、完整授权 UI、图片静态访问保护、`/uploads` 关闭、AI 权限、研究数据访问、生产管理员治理和 Windows 支持。

## Decisions

### 1. Owner、授权和审计数据

- 在病例记录增加非空 `owner_user_id`，外键引用 `users.id`；一个病例始终只有一个 owner，本 Change 不提供转交接口。管理员或启用的病理医生创建病例时，服务端均将当前用户设为 owner；管理员仍可访问全部病例。
- 新增病例访问授权对象，以 `(case_id, user_id, permission)` 表示能力，`permission` 限定 `read`、`edit`、`upload`，并有 `granted_by`、`created_at`、`revoked_at`。部分唯一约束保证每个病例/用户/能力最多一条未撤销授权；撤销保留历史，重新授权创建新记录。
- 只有管理员可授予/撤销授权，且接收者必须是启用的病理医生。有效 `edit` 或 `upload` 仅在同一用户对该病例存在有效 `read` 时成立；管理员授予依赖能力时必须在同一事务内验证或先确保 read。撤销 read 时同事务撤销该用户该病例的 edit/upload，防止悬空能力。所有权本身隐含 read/edit/upload；管理员权限不写入授权表。研究人员始终拒绝临床病例 API，即使存在异常/旧授权行也不得绕过角色上限。
- 新增最小追加式审计对象，只记录 actor、目标病例/用户、操作类型、能力、发生时间和成功/拒绝结果；不得记录病例正文、图片路径、密码、会话/CSRF token 或 Cookie。为保证病例删除后仍可审计，审计不得使用会随病例删除级联的外键；使用不可变病例 ID/标识快照字段或等价的脱关联引用。病例、样本、文字报告删除以及授权授予/撤销必须记录成功操作。审计写入与被审计的成功数据库变更在同一事务中，审计写入失败则变更回滚；拒绝尝试可写不含敏感负载的失败记录，但不能改变资源状态。

### 2. 权限矩阵与统一判定

| 主体 | 读取病例及子资源/分析汇总 | 编辑病例/样本/报告和排序 | 上传样本 | 删除病例/样本/报告 | 授权管理 |
| --- | --- | --- | --- | --- | --- |
| 管理员 | 全部 | 全部 | 全部 | 全部 | 全部 |
| 病理医生 owner | 是 | 是 | 是 | 否 | 否 |
| 病理医生有 read | 是 | 否 | 否 | 否 | 否 |
| 病理医生有 read+edit | 是 | 是 | 否 | 否 | 否 |
| 病理医生有 read+upload | 是 | 否 | 是 | 否 | 否 |
| 病理医生有 read+edit+upload | 是 | 是 | 是 | 否 | 否 |
| 研究人员 | 否 | 否 | 否 | 否 | 否 |

列表查询必须在 SQL 中只返回管理员可见病例或该病理医生 owner/有效 read 授权病例；不得先返回全量数据再依赖前端过滤。单病例和子资源路由必须先验证病例可见性，再验证样本/报告属于该病例，并按所需能力授权。病例不存在和存在但无权访问必须返回相同状态码和等价响应体，不泄露存在性。删除仅管理员执行且以服务端数据库操作为最终权限边界。

### 3. 病例创建和 identifier 冲突

病例创建只允许启用病理医生或管理员发起；不论角色，owner 均由服务端设为当前用户，客户端不得指定或覆盖 owner。对 `identifier` 唯一冲突应使用不执行更新的原子插入语义，将其作为冲突处理返回通用冲突响应。冲突时不得返回既有病例内容，也不得插入任何样本、报告、文件引用或改变 owner；不得使用“先 SELECT 判断再 INSERT”的竞态式实现替代数据库唯一约束保护。收到相同 identifier 不构成已有病例授权。

当前代码没有针对已有病例追加样本的独立接口；本 Change 新增病例样本追加接口（例如 `POST /cases/:caseId/samples`），在写入前要求病例 `upload` 有效能力并复用现有 Origin/session-bound CSRF 校验。前端 service 必须通过该独立接口上传已有病例的样本。不得利用 `POST /cases` 的 identifier 冲突路径追加样本。

### 4. 认证、CSRF 与前端接入

所有病例 API 继续复用既有 `authenticateRequest` 和明确配置的 Origin 检查；所有状态变更必须通过既有 session-bound CSRF 校验，不新建 token 格式、认证方案或旁路。前端调用应带 `credentials: 'include'`，状态变更先取得/刷新会话绑定 CSRF token 并发送 `X-CSRF-Token`。前端正确呈现未登录和无权状态，并仅依据服务端返回的能力信息显示编辑、上传和删除动作；界面隐藏不得作为安全控制。删除和授权仍由后端强制执行。授权管理 API 可由本 Change 提供，但不新增完整管理 UI。

### 5. 旧病例 owner 迁移

使用独立、显式版本化迁移，不依赖普通 GET 或 `db/init.ts`。迁移前由部署/实施输入明确的 `legacy owner mapping`（旧病例集合到具体启用管理员 ID）；不得猜测、选第一个管理员或静默采用默认账户。迁移在单一数据库事务中锁定/校验指定用户及病例集，为所有未归属旧病例设置该 owner，并保留版本、映射摘要和迁移核验记录。迁移前后核对病例总数、每个病例恰有一个有效 owner、owner 均为指定启用管理员、样本/报告/分析的外键关联数量和映射覆盖率。任何映射缺失、管理员禁用、数量不一致、关联变化或迁移异常均回滚整个事务并失败关闭；不提供恢复匿名病例 API 的回退。

### 6. API 覆盖和对象归属

授权范围覆盖 `GET /cases`、病例创建/编辑/删除、样本编辑/删除、文字报告列表/创建/编辑/删除、样本和报告排序及组织切片分析汇总，并覆盖病例路由中所有其他读写/统计端点。聚合查询的病例集合和关联样本/报告/分析必须来自同一已授权病例集合。每个 sampleId/reportId 都必须同时匹配 URL 中的 caseId；不匹配按统一无权/不存在语义处理。文件物理删除继续按既有存储 API 执行，但 `/uploads` 直接 URL 不在本 Change 的授权范围。

## Risks / Trade-offs

- 将 `owner_user_id` 设为非空需要准确的既有病例映射；映射不明确时迁移会阻断，而不是猜测归属。
- 授权与资源变更使用数据库事务确保审计和授权状态原子性；并发撤权与写请求必须按一致的授权读取/锁策略实现，撤销提交后新请求立即无权。
- 病例 API 授权不会保护知道 `/uploads/...` 的直接请求，也不会限制 AI；部署边界必须持续明确。
- 既有前端直接请求可能需要统一调整请求封装；只做权限所需的最小接入，不重构前端架构。

## Migration and Rollback

先在隔离数据库备份并导出病例到指定管理员映射清单，再执行单事务版本化迁移。验证版本记录、病例数量、owner、授权空初始状态及样本/报告/分析关联数量后才允许启用强制授权。迁移或核验失败时回滚事务并保持服务不可用/拒绝受保护请求；不得恢复无鉴权病例接口作为回退。回滚应用版本时，数据库 owner/授权数据不得被静默删除；兼容性回退方案需另行批准。

## Open Questions Requiring Operational Input

- 实施迁移前必须提供旧病例到一个明确、已启用管理员账户的映射并确认病例总数；这不是可由代码默认值解决的选择。
- 管理员或启用的病理医生创建病例时，服务端将当前认证用户设为 owner；管理员不需要额外指定病理医生 owner。所有权转交不在本 Change 范围内。
