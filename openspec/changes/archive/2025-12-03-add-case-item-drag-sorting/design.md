## Context
当前 CancerApp 桌面端的病例侧栏中，“图像”和“文字”两块列表仅按创建时间倒序展示。对于需要教学演示、临床路径复盘或固定模板（如“总体概述→指南诊断→检测/病理→治疗随访”）的场景，用户很自然会希望通过拖拽来编排顺序，并且期望这种顺序在下次打开应用时保持不变。

现有实现特点：
- 数据层：
  - `case_samples` 与 `case_reports` 表没有显式的排序字段，默认用 `created_at` 作为返回顺序依据。
  - `/cases` 路由通过聚合查询返回病例及其样本/报告，查询中按 `created_at` 倒序排序。
- API 层：
  - 尚不存在专门的排序端点，所有顺序变更只能通过“删除后重建”的方式实现。
- 前端：
  - 侧栏列表只支持点击选择/展开、编辑与删除，不支持拖拽或其它排序交互。

目标是在保持现有 API 与数据结构兼容的前提下，引入：
- 每个病例内部“图像样本顺序”和“文字报告顺序”的显式表示；
- 轻量、安全的排序 API；
- 与手机系统类似的拖拽排序交互。

## Goals / Non-Goals
### Goals
- 为 `case_samples` 与 `case_reports` 增加持久化的排序字段，并在所有聚合返回中按该字段排序。
- 提供简单的排序 API，使前端能够将拖拽后的 ID 顺序写回数据库。
- 在侧栏“图像/文字”列表中实现自然的拖拽排序交互，包括可视化让位效果。
- 在失败场景下提供清晰而不打断的错误提示，并回滚到原顺序。

### Non-Goals
- 不改动病例列表本身的排序方式（病例之间仍按创建时间或既有规则排序）。
- 不在本次变更中实现跨病例的复制/移动样本或报告。
- 不扩展到移动端 H5 或微信小程序排序（如有需要可在后续变更中独立规划）。

## Decisions
### 1. 排序字段设计
- 在数据表层面为每个列表增加一个整数排序字段，例如：
  - `case_samples.sort_order INTEGER`
  - `case_reports.sort_order INTEGER`
- 排序规则：
  - 在同一病例内，按 `sort_order` 升序排列；若 `sort_order` 为空，则按 `created_at DESC` 兜底。
  - 新增的样本/报告默认追加在列表末尾（可以采用“当前最大 sort_order + 1”策略）。
- 兼容策略：
  - 对于已存在的记录，在迁移脚本中按 `created_at`（或当前返回顺序）填充分组内的 `sort_order`，保证迁移前后视觉顺序不变。

### 2. 排序 API 形态
- 为每个病例提供两个端点：
  - `PUT /cases/{caseId}/samples/order`
  - `PUT /cases/{caseId}/reports/order`
- 请求体为一个 JSON 对象：
  ```json
  {
    "ids": ["sample-id-1", "sample-id-2", "..."]
  }
  ```
- 行为约束：
  - `ids` 列表必须与该病例当前持有的样本/报告 ID 集合完全一致（既不能缺少，也不能多出）；否则返回 `400` 并附带说明。
  - 更新逻辑在事务中完成：按 `ids` 顺序为每一行写入新的 `sort_order`。
  - 成功时可返回 `204 No Content` 或更新后的病例聚合（根据实现方便程度选择；当前倾向于 `204` 并由前端自行维护本地顺序）。

### 3. 前端交互模式
- 在侧栏“图像”与“文字”列表中采用“长按/拖拽卡片上下移动”的模式：
  - 鼠标或触控板按下某个卡片区域并移动时，进入拖拽状态；
  - 拖动过程中其他卡片按位置顺序自动让位（常见的“占位卡片 + 移动中的卡片浮层”效果）。
- 拖拽结束策略：
  - 在前端先本地更新顺序（保证 UI 立刻响应）；
  - 然后调用对应排序 API 将新顺序写回后端；
  - 若 API 调用失败，则回滚本地顺序并提示错误。
- 可访问性兜底：
  - 在无鼠标或使用键盘时，排序非必需；当前变更不强制提供键盘重排，但必须保证现有键盘选择/编辑体验不被破坏。

### 4. 错误处理与状态反馈
- 排序请求期间：
  - 对应列表的拖拽操作避免并发（可以简单禁用再次拖拽，或排队处理）。
  - 提供轻量的“保存中…”状态指示（如局部 loading 文案或淡入提示）。
- 排序失败：
  - 把列表顺序恢复到拖拽前的状态；
  - 通过 toast 或侧栏内的提示文本告知用户“排序保存失败，请稍后重试”。

## Alternatives Considered
### A. 使用 JSONB 保存顺序（而非列）
方案：使用单独的排序配置表或在 `cases.metadata` 中保存 `sample_order`/`report_order` 数组，然后在查询层合并。

优点：
- 不需要修改已有表结构。
- 理论上可以为不同视图保存多套顺序。

缺点：
- 查询与排序逻辑变复杂，需要在应用层合并顺序与记录集合。
- 一旦样本/报告被删除或新增，排序数组容易与实际数据集合不一致，需要额外同步逻辑。
- 对下游消费（如 BI/分析）不够直观。

结论：出于简单性和可维护性考虑，本次选择显式列 `sort_order`。

### B. 在 `POST /cases` 时附带排序信息
方案：允许在创建病例时通过 payload 指定每个样本/报告的初始顺序，不提供单独的排序端点。

优点：
- 不需要新增 API。

缺点：
- 无法覆盖“后续拖拽调整顺序”的需求。
- 与当前 UI 交互诉求（频繁重排）不匹配。

结论：不采纳，仅保持 `POST /cases` 的初始行为简单清晰。

## Risks / Trade-offs
- **并发排序冲突**：同一病例在多个客户端同时重排可能导致排序覆盖。
  - 缓解：本次优先使用最后写入赢（last-write-wins），并在后续有需要时引入版本号或乐观锁。
- **旧数据迁移**：若排序字段填充不当，可能导致现有病例顺序发生意外变化。
  - 缓解：迁移脚本严格按照当前 `created_at` 排序填充分组内 sort_order，并在测试环境验证。
- **交互复杂度**：拖拽实现不当可能影响已有点击/展开交互。
  - 缓解：将“拖拽热点区域”限制在卡片主体区域，并保留按钮的点击交互优先级；通过简单的拖拽库/自实现确保事件处理清晰。

## Migration Plan
1. 在开发环境中添加排序列并填充旧数据；验证 `/cases` 返回顺序与变更前一致。
2. 实现并测试排序端点，使用本地脚本或 Postman 模拟重排，确认写入行为及边界情况。
3. 在前端接入排序 API 之前，先实现纯本地拖拽排序以验证交互体验；再接入持久化逻辑。
4. 部署到测试环境后重点验证：
   - 旧病例顺序未被破坏；
   - 新增样本/报告的默认插入位置符合预期；
   - 高频排序操作不会引发明显性能问题。

## Open Questions
- 是否需要在某些视图中提供“按时间排序”和“按自定义排序”之间的切换？当前提案假定用户主要使用自定义顺序。
- 长期是否需要对排序操作提供审计记录（例如最后一次排序时间、操作者）？本次变更暂不记录。
