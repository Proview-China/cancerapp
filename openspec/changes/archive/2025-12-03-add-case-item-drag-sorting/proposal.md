## Why
当前桌面端病例侧栏中，“图像”与“文字”列表的顺序完全依赖创建时间，用户无法按自己的思路对影像样本或文字病历进行编排。对于教学/示例数据（例如当前 10 个 demo 文本病例），典型使用场景是希望将“总体概述→指南诊断→检测/病理/分子→治疗/随访”按逻辑顺序排列；在图像维度上，也常需要固定“原图→处理后图像→关键截面”等顺序。  

缺乏可持久化的排序能力会导致：
- 不同会话中病例内容顺序不可控，难以对外演示或录制教程；
- 无法通过简单交互编排多篇报告的阅读顺序，只能依赖命名或重新导入；
- 未来将这些病例用作训练/评估数据时，缺少稳定的“主序列”信号。

## What Changes
- 在数据层为 `case_samples` 与 `case_reports` 引入稳定的排序字段，用于表达每个病例内部“图像样本顺序”和“文字病历顺序”，并在所有 `GET /cases` 聚合结果中按该顺序返回。
- 在 API 层新增轻量的“批量重排”端点，用于接受某病例下样本/报告的有序 ID 列表，完成排序的持久化。
- 在桌面 UI 的“图像”“文字”列表中提供拖拽排序交互：用户按住卡片拖动即可重排，同一列表内其他卡片会自动让位；交互结束后自动调用排序 API 写入后端。
- 确保排序操作安全、可恢复：当网络/保存失败时在 UI 中给出提示，并保持原顺序不被误改；排序的默认行为仍与当前“按创建时间倒序”保持兼容。

## Impact
- Affected specs:
  - `cases`：补充对样本/文字报告内部顺序的建模要求，以及排序 API 合同。
  - `ui`：在病例侧栏“图像/文字”列表中增加拖拽排序交互的规范（含键盘/可访问性兜底行为）。
- Affected code:
  - 后端：
    - `database/schema.sql` 与 `backend/src/db/init.ts`：为 `case_samples` 与 `case_reports` 增加排序字段，并保证默认值/兼容行为。
    - `backend/src/routes/cases.ts`：在聚合与 CRUD 流程中按排序字段返回列表；新增两个排序端点（样本与报告）。
  - 前端（桌面 Electron+Vite）：
    - `frontend/src/services/caseService.ts`：增加排序 API 封装。
    - `frontend/src/components/AnalysisSidebar.tsx`：在“图像”“文字”列表中实现拖拽排序交互，以及失败时的恢复提示。
