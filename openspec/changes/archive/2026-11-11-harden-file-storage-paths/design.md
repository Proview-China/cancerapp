## Context

`POST /cases` 使用 Multer memory storage 接收文件，在数据库事务中调用 `storeFile`，并把返回的 `/uploads/...` 路径写入 `case_samples.storage_path` 和 `storage_thumbnail`。`DELETE /cases/:caseId` 与样本删除路由通过 `deleteStoredFile` 删除这些路径。`server.ts` 将 `config.uploadsRoot` 映射到 `/uploads`，前端 `caseService.ts` 将数据库路径解析为 API URL。

本 Change 只处理存储路径、命名、防覆盖和写入完整性。数据库事务与文件系统无法组成单一事务，因此本 Change 不引入文件状态机或清理任务；实现应记录并测试现有调用边界，后续一致性治理另行提案。

## Goals / Non-Goals

- Goals: 根目录边界校验、拒绝符号链接逃逸、不可预测新名称、拒绝覆盖、同文件系统原子提交、旧路径和访问方式兼容。
- Non-Goals: Schema 变更、旧文件迁移、认证授权、关闭静态访问、图片格式/解码/像素限制、清理任务和文件状态机。

## Decisions

### 受控路径解析

所有内部存储 key 先经过统一解析函数。根目录使用已解析的绝对路径；候选路径使用 `path.resolve`，只有候选路径等于根目录或位于根目录加路径分隔符之下才接受，不能使用未经分隔符处理的字符串前缀判断。输入拒绝绝对路径、空 key、`.`/`..` 组件和编码后仍会形成越界的路径。

写入和删除前检查根目录、临时目录、正式目录以及目标路径的现有组件。对目录和目标使用 `lstat`/`realpath` 等文件系统检查，拒绝符号链接组件；目标若已存在也拒绝通过链接写入。根目录初始化必须确保其自身及受控子目录不是符号链接。检查结果只能作为拒绝条件，不能作为“目标随后一定安全”的并发保证。

临时目录必须由应用创建并由应用独占管理，权限至少应限制为仅运行后端的账户可写（Unix 使用 `0700` 创建或等效的既有受控权限；Windows 使用仅授予该账户的 ACL）。正式目录也不得允许不可信用户写入。每个临时文件使用随机名称和独占创建（`open` 的 `wx`/`O_EXCL` 语义），写入完成并关闭后才进入提交步骤。

### 命名和兼容

正式文件名由后端随机生成的 UUID/等强度不可预测 token 与来自受控白名单的扩展名组成。业务标识、模态和序号不再决定物理文件名；原始文件名仍写入现有 `original_filename` 字段，现有响应字段不变。旧的 `/uploads/<legacy-name>` 记录不迁移，删除操作继续支持其相对路径，但同样必须通过边界和符号链接校验。

### 原子防覆盖提交和跨平台限制

临时目录与正式文件目录都位于同一个 `UPLOADS_ROOT` 文件系统下，例如 `<root>/.staging/` 与 `<root>/`。普通 `rename`/`fs.rename` 不能作为防覆盖原语：在 Linux/POSIX 上它可能原子替换已有目标，Node 当前公开的 `rename` API 也没有 `no-replace` 参数。

首选提交算法是：临时文件写入并关闭后，使用 Node `fs.link` 将临时文件创建为正式目标的硬链接；目标已存在时由文件系统以 `EEXIST` 拒绝，绝不替换已有目录项；确认 link 成功后再 unlink 临时名称。临时文件和目标必须在同一文件系统内。硬链接发布使正式路径一次性指向已完整关闭的文件；link 与 unlink 之间若进程崩溃，可能留下两个名称，但不会覆盖目标，后续状态机 Change 再处理残留临时对象。

`fs.link` 在 Linux/POSIX 文件系统上应以真实文件系统测试确认其原子独占语义；Windows NTFS 通常支持文件硬链接，但权限、文件系统类型、杀毒软件和挂载实现可能导致 `EPERM`、`EXDEV` 或行为差异。Windows 不得把 `fs.rename` 当作等价替代。可选替代方案及限制必须在实现前验证：使用平台原生 `renameat2(RENAME_NOREPLACE)`/`MoveFileEx` 等原生 helper（增加部署和维护复杂度），或使用经验证的原子独占创建 API；“先 `access`/`stat` 再 `rename`”明确不合格。若当前 Node/目标文件系统无法证明 `fs.link` 或原生 no-replace 原语的语义，操作必须失败关闭并给出诊断错误，不能回退到可能覆盖的普通 rename。

写入失败时清理本请求创建的临时文件。提交成功后只清理本请求持有的临时名称；不得根据业务文件名、目录扫描或模糊匹配删除其他请求的文件。清理失败必须记录结构化日志，至少包含请求关联标识、临时路径、正式路径、错误码和清理阶段，不向 API 暴露服务器绝对路径。

清理责任必须按对象区分：临时文件从创建到成功 link/unlink 或失败清理都由本次存储调用负责，并且只能删除其持有的随机 staging 名称；正式文件一旦 link 成功即视为已发布对象，不得在同一调用的数据库回滚处理器中擅自删除，也不得用目录扫描推断归属。若数据库事务随后回滚，留下的正式孤儿文件是已知一致性窗口，记录为后续文件状态机/清理 Change 的输入；本 Change 只要求不误删并保留诊断信息。

`lstat`/`realpath` 与后续 `open`、`link`、`unlink` 之间仍存在 TOCTOU 窗口。应用通过受控目录权限、拒绝符号链接、随机临时名、独占创建和目标不可替换的 `link` 原语缩小该窗口；这不能防御拥有存储根目录写权限的本地攻击者在检查后替换父目录。若威胁模型包含该攻击者，必须改用 Linux `openat2`/`renameat2` 或 Windows 句柄相对路径等原生能力，不能仅靠本 Change 的纯 Node 路径 API。数据库事务回滚后若正式 link 已发布，仍可能留下正式孤儿文件；该问题继续留给后续文件状态机 Change。

### 静态访问兼容

继续挂载 `/uploads`，不改前端 URL 拼接和数据库公开路径格式。`.staging` 必须是 `UPLOADS_ROOT` 下的隐藏受控目录，并在静态服务配置前验证：实现应使该目录及其中内容不可由 `/uploads/.staging/...` 访问（优先由静态访问层显式拒绝，不能只依赖隐藏目录名称）。正式文件仍位于静态根下并保持现有访问方式。认证保护和静态目录关闭明确留给后续 Change。

静态拒绝必须按规范化请求路径或等价的显式路由规则执行，并覆盖编码、重复分隔符和目录索引变体；隐藏目录名称本身不是安全控制。测试必须确认 staging 响应为拒绝/不存在，同时合法旧文件和新正式文件仍可访问。

## Risks / Trade-offs

- 旧文件仍可能使用业务命名，因本 Change 不迁移旧文件，只能保证新写入不复用该命名；旧数据的完整一致性扫描留待后续治理。
- 文件写入发生在现有数据库事务内，事务失败仍可能留下正式孤儿文件；本 Change 不伪装成完整跨系统事务，后续状态机需处理该窗口。
- `fs.link` 的 no-replace 语义和硬链接权限依赖操作系统与文件系统；测试必须在真实临时目录上验证，而不能只测字符串函数。无法验证的平台必须失败关闭。
- 纯 Node 路径 API 无法消除拥有存储根目录写权限的本地攻击者造成的全部 TOCTOU 风险；若该威胁在部署环境成立，需要原生句柄相对路径能力的独立设计。

## Migration Plan

无需数据库或旧文件迁移。部署后新文件使用随机名称，旧 `storage_path` 继续按原格式读取。回滚代码时，新路径仍是合法 `/uploads/<filename>`，不会要求数据库字段回填；新文件由后续人工/清理流程按现有删除逻辑处理。

## Open Questions

- 是否需要在后续文件对象 Change 中记录 staging/active 状态，以解决数据库提交与文件移动之间的中断窗口。
- 是否需要在后续认证 Change 中取消无条件的 `/uploads` 静态访问。
- 目标部署平台和文件系统是否承诺 `fs.link` 的原子创建、不替换和权限语义；若不承诺，应选择并维护平台原生 no-replace helper。
