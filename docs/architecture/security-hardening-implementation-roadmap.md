# CancerApp 第一阶段安全与数据完整性治理路线图

## 1. 范围和原则

本路线图基于当前分支 `feature/ihc-pathology-analysis`、提交 `4201a39`、`docs/architecture/security-and-data-integrity-plan.md`、当前源码和 `database/schema.sql` 制定。阶段 1 的受控存储核心和阶段 4 的认证基础已在 2026-11-11 归档交付；其余阶段仍是规划，不代表已实施。

截至 2026-11-11，认证验收记录见 `docs/acceptance/2026-11-11-authentication.md`。该记录不扩大认证 Change 的边界：`/cases`、`/uploads`、`/ai` 授权、受保护图片访问、图片内容校验、文件状态/清理、依赖治理和生产管理员治理仍待后续批准 Change。

部署目标是 Electron + React 桌面端、Node.js + Express 后端、PostgreSQL 和本地文件存储。当前优先支持单机部署，同时保留未来多人内网访问的边界。角色固定为系统管理员、病理医生和研究人员。

安全改动应先经过 OpenSpec 变更提案和批准。依赖升级、测试补充和恢复既有设计意图的窄范围修复可以按项目规则单独处理，但涉及认证、数据库表、文件对象或访问模型的改动必须先做设计确认。

本文中的“已确定”是指可以作为实现约束的安全原则；“待批准”是指需要项目负责人在实施前选择的业务规则、格式上限或 Schema 方案。当前可以确定：不能以无鉴权静态目录作为正式生产回退，文件状态必须可恢复，访问控制必须由后端执行，依赖必须分组升级。尚待批准：文件对象表还是字段扩展、病例默认所有权、病理医生删除权限、研究人员原图范围、图片格式和容量上限。

## 2. 当前问题证据

- 历史基线中 `POST /cases` 使用业务字段拼接名称并可能覆盖同名文件；该命名和写入风险已由归档的 `harden-file-storage-paths` Change 处理。数据库事务和文件系统仍非单一事务，数据库失败后的正式孤儿文件治理仍延期。
- `DELETE /cases/:caseId` 和 `DELETE /cases/:caseId/samples/:sampleId` 在数据库提交后调用 `deleteStoredFile`，删除失败只记录 warning。
- `/uploads` 仍保留兼容的静态访问，尚无病例授权；但文件删除现已经过受控根目录和符号链接边界校验，`.staging` 不对静态请求开放。
- Multer 仅设置了 200 MB 单文件和 20 文件限制，没有 `fileFilter`、文件头检查、图像解码检查或像素限制。
- `database/schema.sql` 的 `case_samples` 只保存路径、缩略图路径和校验和，没有文件状态、大小、MIME 或文件对象 ID。
- 历史基线中的“没有用户、会话、登录、角色”已由认证 Change 补齐；病例访问授权和静态图片保护仍未实施，不能把认证基础视为病例授权。
- 后端直接依赖包括 `express@4.21.2`、`multer@2.0.2` 和 `uuid@9.0.1`；昨天审计得到 21 项漏洞，其中 14 high、2 critical。

## 3. 角色和权限边界

| 能力 | 系统管理员 | 病理医生 | 研究人员 |
|---|---:|---:|---:|
| 登录、退出、修改自己的密码 | 是 | 是 | 是 |
| 用户启用、停用、角色管理 | 是 | 否 | 否 |
| 创建和编辑病例基本信息 | 是 | 是本人创建或明确授权的病例 | 仅在病例授权范围内 |
| 上传病例图片 | 是 | 是本人创建或明确授权的病例 | 默认否，需明确授权 |
| 删除病例和原始图片 | 是 | 待批准，建议需显式授权 | 否 |
| 查看病例和原始图片 | 是 | 本人创建或明确授权的病例 | 仅授权病例，默认脱敏 |
| 编辑文字病历和临床备注 | 是 | 本人创建或明确授权的病例 | 默认否 |
| 查看和维护病理分析结果 | 是 | 是 | 查看授权结果，不能修改临床结论 |
| 导出脱敏训练样本 | 是 | 可申请/审核 | 是，限研究数据 |
| 管理数据集、标签和版本 | 是 | 可提供标注 | 是 |
| 删除病例和文件 | 是 | 需授权 | 否 |
| 查看审计日志和孤儿文件报告 | 是 | 否 | 否 |

角色只是第一层控制。推荐采用“角色 + 病例所有权 + 显式授权”三层判断：所有者拥有基础管理权，显式授权可以授予或撤销特定用户的读取、编辑、上传、分析和导出能力，角色限制最高权限上限。病例创建者默认成为所有者，但是否允许创建后转交、是否允许多人共同所有，仍待批准。前端隐藏按钮不能替代后端授权。

## 4. 分阶段实施路线

### 阶段 0：安全边界和基线确认

**当前问题和证据**：认证 Change 已使 Electron 使用绑定回环地址的 localhost 页面和认证接口；病例资源授权、多用户部署边界及原始图片权限仍未完成确认。

**目标设计**：已交付认证层面的本机监听和登录基础；仍需确定管理员生产初始化、三个角色的病例授权规则、原始图片访问规则和数据保留规则。形成完整权限矩阵和威胁边界，明确研究数据必须脱敏。

**涉及文件和对象**：文档、部署说明、未来 OpenSpec Change；暂不改源码或 Schema。

**Schema/迁移**：不需要。

**前端/Electron 影响**：暂不改动；后续登录状态放在受控会话中，不使用长期 localStorage 令牌。

**测试和验收**：权限矩阵获得确认；列出管理员、病理医生、研究人员对病例、原图、分析结果和数据集的允许/拒绝场景。

**风险和回滚**：设计分歧会导致后续重复开发。开发环境可以使用明确标记的测试账户或测试绕过配置，但无鉴权访问不能作为生产回退；真实病例环境必须在认证和授权完成后使用。

**工作量**：低。**依赖**：无。

### 阶段 1：文件对象和安全存储核心（核心存储已交付，文件对象状态延期）

**当前问题和证据**：文件名由业务字段拼接，直接写入 `UPLOADS_ROOT`；数据库只存公开路径字符串，无法可靠追踪文件状态。

**目标设计**：使用不可预测的存储对象 ID 与原始文件名分离。上述受控存储核心已交付并使用 staging 独占写入与 `fs.link` no-replace 提交，不使用普通 rename；路径边界、符号链接和 `.staging` 静态隔离已有测试。文件对象状态、清理任务和旧文件迁移仍延期；现有 `/uploads` 兼容访问保留，直到受保护下载 Change 完成。

**涉及文件和对象**：`backend/src/utils/fileStorage.ts`、`backend/src/routes/cases.ts`、`backend/src/server.ts`、前端 URL 映射服务；建议新增 `file_objects` 表或在 `case_samples` 增加受控对象字段、大小、MIME、状态和哈希。

**Schema/迁移**：若采用 `file_objects` 表，需要新增表和旧 `case_samples` 数据迁移；若先采用 `case_samples.storage_key` 等字段，需要新增字段并从现有 `storage_path` 解析迁移。不能直接覆盖旧路径，迁移前必须建立备份和映射报告。

**前端/Electron 影响**：前端不再假定数据库字段是公开 URL，改由后端返回受保护的预览/下载地址。Electron 需要处理下载失败和权限失败。

**测试和验收**：重复文件名、并发上传、目标已存在、绝对路径、`..`、符号链接和异常 Unicode 文件名测试通过；文件内容哈希与数据库一致；任何写入路径都落在配置根目录内。

**风险和回滚**：旧路径迁移错误可能导致图片不可见。先支持旧字段只读兼容，完成映射核对后再切换读取；保留旧文件和数据库备份，出现问题时回退读取旧字段。旧公开路径只能作为开发/迁移期间的受控兼容能力，必须绑定本机、记录使用情况并明确禁止用于生产，不能作为认证失败时的回退。

**工作量**：高。**依赖**：阶段 0；会影响阶段 2、3。

### 阶段 2：上传、删除和孤儿文件治理

**当前问题和证据**：上传文件在事务前写入，SQL 失败时不会清理；删除提交后清理文件，失败只打印 warning；级联删除只覆盖数据库对象，不覆盖文件系统。

**目标设计**：采用文件状态机：`staging`、`active`、`deleting`、`deleted`、`cleanup_failed`，并记录尝试次数、最后错误、更新时间和幂等操作 ID。执行顺序如下：

1. 请求生成唯一 object ID，在存储根目录下创建临时文件；临时文件使用独占创建，不能覆盖已有对象。
2. 校验文件格式、大小、哈希和路径，失败时删除临时文件并结束请求。
3. 开启数据库事务，写入文件对象和病例样本记录，状态为 `staging`；事务失败只回滚数据库并删除临时文件。
4. 事务提交成功后，将临时文件原子移动到正式 object key；移动成功后将状态更新为 `active`。若进程在提交后、移动前崩溃，恢复任务根据 `staging` 记录和临时文件继续移动或清理。
5. 删除时先在事务中将对象标记为 `deleting`，保留引用和删除任务；提交后执行幂等文件删除，成功后更新为 `deleted`，失败进入 `cleanup_failed` 并按退避策略重试。
6. 孤儿扫描比较数据库中的 active/staging/deleting 对象与磁盘文件清单，只报告未知文件、缺失文件和状态不一致；自动删除必须经过管理员批准或明确的保留期。

数据库状态和文件系统不可能由一个事务完全同步，因此目标是让每种中断状态都有明确的恢复动作，避免长期不可见的不一致。

**涉及文件和对象**：`cases.ts`、`fileStorage.ts`、新增文件清理 service/worker、`file_objects` 或清理任务表、病例删除和样本删除接口。

**Schema/迁移**：需要新增文件状态、删除时间和错误信息；若采用清理任务表，需要新增表。旧记录迁移为 `active` 前必须检查文件是否存在并输出缺失清单。

**前端/Electron 影响**：上传失败显示可重试错误；删除成功应表示数据库操作和清理状态已经被记录，不应把后台重试误报为文件已彻底删除。管理员增加清理报告入口可后置。

**测试和验收**：模拟数据库插入失败、事务失败、文件权限失败、进程中断、重复请求和部分删除失败；确认无未记录文件、可重试任务可恢复，病例级删除只影响其级联对象和关联文件。

**风险和回滚**：清理任务设计错误可能误删文件。默认只删除有明确数据库引用和 object key 的文件；孤儿扫描先只报告不删除，删除动作需要管理员确认。迁移期间保留旧文件和旧字段读取能力，但不保留无鉴权生产访问。任何任务重复执行必须安全，失败时恢复到上一个可识别状态而不是直接删除记录。

**工作量**：高。**依赖**：阶段 1。

### 阶段 3：图片格式和资源限制

**当前问题和证据**：当前只有 Multer 的 200 MB 单文件、20 文件限制，没有 MIME、magic bytes、真实解码、尺寸和像素限制。

**目标设计**：建立图片白名单和资源策略，例如 JPEG、PNG、TIFF 是否允许需要确认；校验请求 MIME、文件头和真实解码结果；限制宽度、高度、总像素、单请求总大小和解码内存；拒绝异常图片并清理临时文件。

**涉及文件和对象**：`cases.ts` 的 Multer 配置、文件校验 service、`file_objects` 元数据字段、前端错误展示；依赖升级独立处理。

**Schema/迁移**：若文件对象表已在阶段 1 建立，只增加或使用 `mime_type`、`size_bytes`、`width`、`height`、`format`；否则需要新增字段。旧文件的尺寸和格式可通过离线扫描补齐，不能在请求时假定已有值。

**前端/Electron 影响**：上传前可做友好提示，但后端必须再次验证。错误信息应区分格式、尺寸和容量，不能泄露服务器路径。

**测试和验收**：合法图片、错误扩展名、伪造 MIME、损坏图片、超大像素、超大请求、过多文件和中断上传均有测试；验证拒绝后无数据库记录和临时文件。

**风险和回滚**：过严限制可能拒绝现有医学图像格式。先以配置化白名单和报告模式收集现有文件情况，确认格式后启用拒绝策略；保留明确的开发环境测试配置，不允许生产绕过。

**工作量**：中到高。**依赖**：阶段 1，最好在阶段 2 后完成。

### 阶段 4：认证、会话和三角色授权（认证基础已交付，病例授权延期）

**当前问题和证据**：用户表、登录接口、Cookie 会话、CSRF、限速和账户状态操作已交付并通过认证验收。下述原始认证方案不表示三角色病例授权已经实现；病例访问控制和 `/uploads` 授权仍未实施，仍属于后续阶段。

**目标设计**：新增用户、会话、角色和病例访问关系。密码使用 Argon2id 或 bcrypt 哈希；登录使用 Electron 可管理的 HttpOnly Cookie 会话，Cookie 设置 `HttpOnly`、`SameSite`，多人内网 HTTPS 部署时设置 `Secure`。所有改变状态的请求使用 CSRF token 或等价的双重提交校验。后端增加认证中间件、角色中间件和病例访问检查。

会话要求包括：登录成功后建立短期会话；Cookie 不写入 localStorage；退出登录时服务端撤销会话并清理 Electron session；会话过期、用户被禁用或密码重置后立即拒绝后续请求；登录失败和会话撤销应记录必要审计信息但不得记录密码。病例请求必须同时检查角色、所有权或显式授权。病例创建默认归创建者所有；转交必须由管理员或当前所有者执行并留下审计记录；授权撤销立即影响病例、样本、分析、原图和导出接口。

研究人员默认只能访问已脱敏、已授权的研究数据。是否允许病理医生查看研究导出结果、是否允许任何角色下载未脱敏原图、病例删除是否需要二次确认和审计，均待批准。

**涉及文件和对象**：新增 `auth` 路由和 middleware，`server.ts` 中间件注册，所有病例/报告/分析路由，受保护的文件下载路由，前端登录状态和 Electron session 生命周期。

**Schema/迁移**：需要新增 `users`、`sessions`、`case_access` 或等价表；现有病例必须制定归属迁移策略，例如由首个管理员拥有。不能把现有病例默认开放给所有角色而不记录决策。

**前端/Electron 影响**：增加登录页、会话过期处理、无权限提示和角色相关操作显示。前端权限只用于体验，后端仍需逐请求校验。

**测试和验收**：未登录请求全部受保护接口被拒绝；三个角色分别验证病例创建、编辑、删除、原图下载、分析查看、数据集导出；跨病例 ID 替换不能越权；会话过期、退出、禁用用户和 CSRF 场景通过。

**风险和回滚**：认证上线可能阻断现有桌面流程。先增加开发测试用户和隔离测试环境，在真实数据前完成迁移演练；保留受保护的管理员恢复入口，但不得保留无认证生产旁路。若登录服务故障，允许显示离线错误和重试，不允许自动退回公开病例或图片访问。

**工作量**：高。**依赖**：阶段 0、阶段 1；文件下载授权必须在受保护存储完成后切换。

### 阶段 5：受保护图片访问

**当前问题和证据**：`server.ts:12` 使用公开静态目录，任何知道路径的客户端都可能请求文件，当前没有病例权限检查。

**目标设计**：认证、病例授权和受保护下载接口必须全部完成并通过测试后，才能关闭现有静态访问。过渡期间不直接把旧 `/uploads` 当正式回退：可在明确的迁移环境中保留只读兼容路径，但应限制到本机、记录访问、禁止真实多人部署，并设置关闭条件。最终新增 `GET /files/:fileId` 或病例样本下载接口；接口查文件对象、病例关系和当前用户权限后再流式发送。Electron 预览使用该接口，响应设置合理的 `Content-Type`、`Content-Disposition` 和缓存策略。

**涉及文件和对象**：`server.ts`、文件访问 controller/service、`file_objects`、前端 `caseService.ts` 和图片组件。

**Schema/迁移**：依赖阶段 1 的文件对象和阶段 4 的用户/病例访问关系；不应继续把公开路径当作授权凭据。

**前端/Electron 影响**：图片 URL 需要带会话 Cookie；加载失败、401/403 和已删除文件需要分别显示。

**测试和验收**：先验证 Cookie 会话、CSRF、过期、退出、禁用用户、所有权转交和授权撤销；再验证未登录、无病例权限、错误 file ID、路径穿越、符号链接、已删除文件均不能获得内容；有权限的三个角色只能得到授权资源；响应不暴露绝对路径。只有在新接口和旧路径关闭演练均通过后，才允许移除 `express.static`。

**风险和回滚**：切换后旧前端缓存 URL 可能失效。先让前端切换到受保护接口，再在测试环境验证旧 URL 全部失效且合法会话仍可预览，最后关闭静态目录。回滚只能回到受保护下载接口的上一版本，不能恢复无鉴权生产访问。

**工作量**：中到高。**依赖**：阶段 1、阶段 4。

### 阶段 6：依赖漏洞分组治理

**当前问题和证据**：后端审计有 21 项漏洞：1 low、4 moderate、14 high、2 critical。直接依赖包括 Express、Multer、uuid 和开发依赖 Vitest；其他为间接依赖。

**目标设计**：先核实每项漏洞的实际影响、调用路径、当前安装版本和可用修复版本，再小批次更新。生产依赖和开发依赖分开治理，禁止盲目全量升级。

**升级分组**：

1. 生产组：先核实 Express 4.x 及 `body-parser`、`path-to-regexp`、`proxy-addr`、`qs` 的修复链，尽量保持 Express 4 主版本。
2. 生产组：单独核实 Multer 的修复版本，再升级 Multer；重新验证 multipart 限制、格式校验和失败清理。
3. 生产组：单独评估 uuid；审计显示受影响版本低于 11.1.1，可用修复显示为 14.0.3，需检查 ESM/API 和 Node 兼容性。
4. 开发测试组：Vitest 与 `@vitest/mocker`；只影响开发测试，但不能暴露 Vitest UI。
5. 开发构建组：Vite、Rollup、PostCSS、source-map-js 及 glob 工具链；确认不会影响 Electron 构建。

**涉及文件和对象**：`backend/package.json`、`backend/package-lock.json`、必要时前端 package 文件；不涉及数据库 Schema。

**Schema/迁移**：不需要。**旧数据迁移**：不需要。

**前端/Electron 影响**：Express/Multer 影响后端 API 和上传；Vite/Rollup 影响构建；uuid 需要重新构建 Electron 和后端。

**测试和验收**：每组先保存审计报告和依赖树，再只修改该组 package.json/lock 文件；执行锁文件安装、后端测试、后端构建、前端构建、Electron 启动检查、上传相关测试和再次 `npm audit`。记录剩余漏洞、生产/开发归属和兼容性结论。不得执行 `npm audit fix` 或 `--force`。

**风险和回滚**：每组独立提交，发现兼容性问题回退该组 package.json 和 lock 文件；不覆盖其他已完成任务。

**工作量**：中。**依赖**：可与阶段 1-5 分开，但 Multer 升级应在上传校验前或同步完成。

## 5. 可不改 Schema 的修复与必须迁移的改造

### 可先不改数据库

- 对写入路径进行 `path.resolve` 根目录边界校验。
- 使用 UUID/object key 生成新文件名，禁止覆盖。
- 增加 MIME、magic bytes、解码、尺寸和资源限制。
- 在请求内维护文件补偿清理列表。
- 在认证、授权和受保护下载接口完成前，不关闭现有访问能力；可以先实现受保护下载接口并在隔离环境验证，不能把无鉴权访问作为生产回退。
- 增加后端认证中间件的骨架和单元测试，但正式用户持久化仍需要 Schema。

这些改动也可能改变 API 行为，正式实施前应确认是否属于现有 OpenSpec 能覆盖的修复。

### 需要新增对象或迁移

- `file_objects`、清理任务或文件状态字段。
- 用户、会话、病例访问关系和角色字段。
- 从旧 `storage_path` 迁移到 object key、哈希、MIME 和状态。
- 将现有病例分配给管理员或其他初始拥有者。

迁移流程必须是：停止写入或进入维护模式；备份数据库、Schema 和文件目录；生成旧文件清单、大小、哈希、路径和数据库映射；以临时目录和新字段写入迁移结果；执行数据库迁移；完成后做数据库到文件、文件到数据库的双向一致性扫描；保存报告后才切换读取。迁移中断时保留旧字段和旧文件，按清单恢复临时对象，不删除旧对象。只有连续核验通过后才允许把新字段作为主读取路径。失败恢复必须能回到旧字段、旧路径和旧接口；旧接口仍不得作为无鉴权生产方案。

## 6. 推荐顺序

推荐顺序为：

1. 阶段 0：确认安全边界、权限矩阵和数据保留规则。
2. 阶段 1：确定文件对象方案、迁移兼容策略和受控存储核心；此时不关闭旧访问。
3. 阶段 2：完成上传失败补偿、删除重试和孤儿扫描。
4. 阶段 3：增加图片格式和资源限制；Multer 生产依赖先完成漏洞核实后再单独升级。
5. 阶段 4：实施用户、Cookie 会话、CSRF、三角色、所有权和显式病例授权。
6. 阶段 5：实现受保护图片接口，完成前端/Electron 切换和全量权限测试。
7. 阶段 5 验收通过后：关闭旧静态目录，不保留无鉴权生产回退。
8. 阶段 6：按生产依赖、开发测试依赖、开发构建依赖分组治理并回归。

依赖核实可以从阶段 0 后单独开始，但生产依赖的实际升级应在上传校验方案冻结后进行，避免同时改变上传行为和排查安全问题。阶段 5 的受保护接口和旧静态目录关闭验收完成前，不应将系统用于真实患者数据的多人访问。

## 7. 总体验收标准

- 所有文件写入和删除路径都能证明位于配置的存储根目录内。
- 重复、并发、损坏和超限上传不会覆盖已有文件，也不会留下未记录文件。
- 数据库失败、进程中断和文件权限失败都有可观察、可重试的结果。
- 未登录或无病例权限的请求不能读取病例数据和图片。
- 三个角色的允许和拒绝矩阵都有后端自动测试。
- 依赖升级按组完成，lock 文件可重复安装，测试、构建和审计结果均有记录。
- 旧文件和旧病例迁移前后都有清单、哈希和回滚依据。
- 认证、病例授权和受保护图片接口全部通过测试后，旧静态目录才关闭；不存在无鉴权生产回退。

## 8. 待确认事项

1. **病例权限模型**：确认采用“角色 + 所有权 + 显式授权”三者结合。影响是权限最清晰，但需要 `case_access` 和所有权迁移；若只采用角色，实施简单但无法支持病例级隔离。
2. **病例转交和删除**：确认谁可以转交所有权、病理医生是否能删除病例/原图、删除是否需要管理员二次确认。影响数据恢复、审计和临床责任边界。
3. **研究人员原图范围**：确认研究人员是否只能访问脱敏副本，还是在显式授权下可以访问原图。影响脱敏流程、文件对象权限和数据合规风险。
4. **原图访问模式**：确认是否必须长期在线预览，还是只允许受保护的临时下载。影响缓存策略、Electron Cookie 使用和旧静态目录关闭时机。
5. **文件对象 Schema**：确认新增 `file_objects` 表，还是扩展 `case_samples`。前者追踪和复用更清晰，但迁移量更大；后者改动较小，但分析图和多引用文件的管理能力有限。
6. **旧数据迁移**：确认旧上传目录和数据库记录是否包含需要保留的真实数据；当前无法从已停止的测试实例判断真实数据规模。
7. **图片限制**：确认允许格式、单图大小、总像素、单请求总大小和磁盘配额。影响现有医学图像兼容性和内存风险。
8. **依赖版本策略**：确认是否允许 uuid 跨主版本升级，以及是否维持 Express 4.x。影响 API、ESM 和 Electron/Node 构建兼容性。
9. **变更拆分**：确认认证/授权、文件一致性、受保护图片访问和依赖治理是否分别建立 OpenSpec Change。拆分越细回滚越容易，但提案和验收数量更多。
