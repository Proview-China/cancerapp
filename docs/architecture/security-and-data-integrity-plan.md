# CancerApp 安全与数据完整性专项方案

本文基于当前分支 `feature/ihc-pathology-analysis` 的源码、`database/schema.sql`、后端锁文件和 2026-11-07 的测试记录整理。历史风险段落保留当时的审查基线；截至 2026-11-11，认证基础和受控文件存储已分别通过验收并归档，后续状态以 `docs/acceptance/2026-11-11-authentication.md` 和归档 Change 为准。

## 0. 当前交付状态（2026-11-11）

- 已交付：Argon2id Cookie 会话认证、CSRF/Origin 校验、限速、账户状态操作、认证迁移和相关测试。
- 已交付：受控存储根目录、路径/符号链接边界检查、随机物理名称、staging 独占写入、`fs.link` no-replace 提交、删除校验及 `.staging` 静态隔离。
- 保留延期：病例级访问控制、受保护图片下载接口、图片内容/MIME/像素校验、文件状态和孤儿清理、依赖漏洞治理、生产管理员初始化/恢复及生命周期锁的生产部署验证。

## 1. 当前状态和审查边界

当前系统由 Electron/React 桌面端、Express/Node.js 后端、PostgreSQL 和本地文件系统组成。后端通过 `backend/src/db/pool.ts` 使用 `DATABASE_URL` 连接数据库，通过 `backend/src/utils/fileStorage.ts` 使用 `UPLOADS_ROOT` 保存上传文件。`backend/src/server.ts` 将整个 `UPLOADS_ROOT` 映射为公开的 `/uploads` 静态目录。

昨天在独立 PostgreSQL 16 实例上验证过：数据库初始化后有 10 张业务表、24 个索引和 6 个更新时间触发器，应用用户只能访问测试数据库。今天测试实例已停止，因此本报告没有重新连接数据库，也没有访问原 PostgreSQL 5432 实例。

本段是 2026-11-07 的历史基线。当前已存在认证路由、服务端 Cookie 会话和认证中间件，但 `/cases`、`/uploads`、`/ai` 仍按认证 Change 的非目标边界运行，病例归属校验尚未交付。

## 2. 上传、删除和一致性风险

### 2.1 文件名重复和覆盖

本段描述的是文件存储 Change 之前的实现。当前新文件使用后端随机物理名称、受控 staging 目录和 no-replace 提交；旧路径保持兼容。图片内容校验和文件对象状态仍未交付。

故障场景：并发创建同一病例、重复导入同一病例，或数据库中的样本数量与目录状态不一致时，两个请求可能写入同一路径，数据库记录中的路径和校验和随后指向最后一次写入的内容。

建议：后端生成不可预测的存储 ID，例如样本 UUID 或随机 UUID；原始文件名只作为展示字段。写入使用 `open(..., 'wx')` 或临时文件加原子 rename，发现目标存在时拒绝覆盖。数据库可增加存储对象唯一标识或唯一约束，但不应依赖文件名作为业务 ID。

涉及文件：`backend/src/routes/cases.ts`、`backend/src/utils/fileStorage.ts`、`database/schema.sql`、前端只需继续传递原始文件名。测试应覆盖同名并发上传、重复导入和目标文件已存在三种情况。

### 2.2 文件成功、事务失败

`POST /cases` 在事务中调用 `storeFile`，文件写盘发生在 `client.query('COMMIT')` 之前。若后续 SQL、约束或提交失败，`ROLLBACK` 只回滚数据库，当前代码没有删除本次已写入的文件。

建议采用“暂存文件 + 数据库提交后确认”的流程：先写入受控临时目录，数据库记录保存临时对象 ID；事务成功后原子移动到正式目录并更新状态。若继续使用当前流程，至少维护本次请求写入文件列表，在回滚分支清理；清理失败应记录可重试的清理任务。更稳妥的方案需要一个文件对象状态或清理任务表，属于数据库和接口设计变化，应先走 OpenSpec。

测试应模拟插入失败、提交失败和文件清理失败，确认数据库没有记录、正式目录没有孤儿文件，并且清理失败可被发现。

### 2.3 数据库删除成功、文件删除失败

`DELETE /cases/:caseId` 和 `DELETE /cases/:caseId/samples/:sampleId` 先提交数据库删除，再调用 `deleteStoredFile`。删除文件失败只打印 warning，接口仍可能返回成功。`ON DELETE CASCADE` 会删除关联样本、报告和组织分析，但不会自动删除文件系统对象。

建议把删除状态记录下来：数据库删除后将文件对象放入待清理队列，清理成功后标记完成；或保留软删除记录直到文件清理完成。无论选择哪种方式，都应提供失败重试和管理员可见的孤儿文件检查。不要把文件删除放进数据库事务中，因为 PostgreSQL 无法回滚文件系统操作。

测试应覆盖文件不存在、权限不足、路径损坏和部分文件删除失败，确认 API 状态、数据库状态和清理状态一致。

### 2.4 格式、MIME、尺寸和内容验证

当前 Multer 使用 `memoryStorage`，限制单文件 200 MB、单请求 20 个文件，但没有 `fileFilter`，后端也没有检查 MIME、真实文件头、图像尺寸、像素数量或解码结果。文件扩展名来自 `originalname`。

建议分层限制：

1. 限制请求体、文件数、单文件大小和总大小。
2. 对允许的图片格式做白名单校验，校验 MIME 和 magic bytes。
3. 使用图像解码器验证文件确实可解码，并限制宽高、总像素和异常压缩比。
4. 将原始文件作为不可执行对象存储，文件名和响应头不允许用户控制脚本类型。
5. 上传失败时清理内存和临时文件。

涉及 `backend/src/routes/cases.ts`、`backend/src/utils/fileStorage.ts` 和依赖选择。由于 Multer 当前存在审计漏洞，格式校验和依赖升级应分开设计、分别测试。

### 2.5 路径校验和静态访问

当前仍保留既有 `/uploads` URL 兼容方式，但文件写入和删除已统一经过根目录、路径穿越和符号链接校验，`.staging` 已显式禁止静态访问。认证授权和受保护下载接口仍属于后续 Change。

建议：数据库只保存内部 object key，不保存任意绝对路径；读写前使用 `path.resolve` 并确认结果位于 `UPLOADS_ROOT` 下；拒绝绝对路径、`..`、符号链接逃逸和不符合对象 ID 格式的路径。静态访问应改为经过认证的下载接口，根据当前用户和病例 ID检查权限后再 `sendFile`；对于本机单用户模式，也至少把静态目录绑定到本机并明确这是受限部署假设。不要仅依赖路径不可猜测来实现授权。

测试应覆盖 `..`、绝对路径、符号链接、编码后的路径、未授权病例和已删除样本的访问。

### 2.6 病例、样本和图片关系

数据库关系是 `cases -> case_samples -> sample_tissue_analysis`，病例删除通过外键级联删除数据库记录。图片本体在文件系统，`case_samples.storage_path`、`storage_thumbnail` 和 `checksum` 只是关联信息。当前没有文件对象表、文件状态、大小、MIME、实际格式或删除状态字段，因此无法从数据库可靠判断文件是否仍存在或内容是否与记录一致。

建议后续增加文件对象和一致性检查设计：记录 object key、大小、MIME、内容哈希、状态、创建和删除时间，并提供只读一致性扫描。病例级删除必须明确级联范围，尤其是组织分析的 `raw_image_path` 和 `parsed_image_path` 是否指向同一文件对象，不能假定它们一定与 `case_samples.storage_path` 相同。

## 3. 认证和授权设计

认证基础已交付并有验收记录；Electron 通过受控 localhost 页面使用 Cookie 会话。病例、图片和 AI 路由的病例级授权仍未交付，`/uploads` 也尚未替换为受保护下载接口。

### 3.1 推荐的轻量方案

现阶段建议采用适合单机或内网部署的最小方案：

- 增加用户表，保存用户 ID、登录名、密码哈希、角色、启用状态和时间字段。
- 后端提供登录和退出接口，密码只保存 Argon2id 或 bcrypt 哈希。
- 使用 HttpOnly、Secure、SameSite 会话 Cookie；Electron 通过受控请求使用会话，不在 localStorage 保存长期令牌。
- 角色先设为 `admin` 和 `operator`。管理员管理账户和病例，操作员管理分配给自己的病例。
- 病例增加 owner 或 access grant 关系；所有病例、样本、报告、分析和文件读取都通过病例权限检查。
- Electron 仍限制后端绑定 `127.0.0.1`；若未来支持多用户内网部署，则必须增加 HTTPS、CSRF 防护、会话失效和审计日志。

不建议当前直接引入大型 OAuth、微服务身份平台或复杂权限模型。认证、病例授权和静态文件授权属于跨模块安全变更，实施前需要 OpenSpec Change。

### 3.2 文件访问

推荐取消无条件的 `express.static(config.uploadsRoot)`，改用受保护的下载路由：先查文件对象和所属病例，再执行权限判断，最后以流方式发送文件。预览接口也应经过相同授权。管理员和普通操作员的差异应在后端判断，不能只隐藏前端按钮。

## 5. 前端 lint 治理方案

昨天和今天的结果一致：38 个错误、7 个警告。

### A. 优先修复潜在功能问题

- `CasesWorkspace.tsx:134` 缺少 `selectedReport` 依赖。
- `CasesWorkspace.tsx:966` 缺少 `images` 和 `onImagesChange`。
- `VisualizationPanel.tsx:188` 缺少 `caseId`。
- `VisualizationPanel.tsx:305` 缺少 `confidence` 和 `riskScore`。
- `VisualizationPanel.tsx:534` 缺少 `caseId` 和 `confidence`。
- `VisualizationPanel.tsx:708` 依赖了可变 ref，并缺少 `riskScore`。

不能机械地把所有依赖加入数组。应先确认是否需要 `useCallback` 稳定父组件回调，或拆分 effect；重点测试切换病例、样本和报告后，界面不会显示上一个对象的数据。验收标准是 lint Hook 警告清零，并通过病例切换、图片切换和分析面板切换测试。

### B. 类型安全

- `caseService.ts` 的响应映射和 `jsonRequest<any>` 共 7 处使用 `any`。
- `CasesWorkspace.tsx` 的图片、分析和元数据处理共多处使用 `any`。
- `VisualizationPanel.tsx` 的 ECharts 模块、元数据、图表 formatter 和统计数据使用 `any`。

建议先定义 API 原始响应类型，再定义分析元数据和 ECharts 最小事件类型；必要时在网络边界做运行时校验。验收标准是消除 `no-explicit-any`，构建通过，病例和图表页面的类型行为不变。

### C. 普通规范问题

- `VisualizationPanel.tsx:458-468` 使用 `var`，需要在确认分支作用域后改为 `let` 或 `const`。
- `textReports.ts:10` 有多余的 `\\!` 转义。
- `electron/main.cjs:25` 存在未生效的 eslint-disable 注释。

这些问题风险较低，最后处理。验收标准是 lint 无错误和警告，构建及 Electron 视觉检查仍通过。

## 6. 病例体系与数据集体系

当前两套体系应暂时保持独立：病例体系服务临床病例浏览和分析，数据集体系服务训练样本、标签和版本。直接把 `cases` 和 `datasets` 合并会把临床记录、训练数据和脱敏流程耦合在一起，增加权限和数据泄漏风险。

后续建议增加明确的导出关系，而不是直接复用同一张样本表：

```text
case_samples
  -> dataset_exports
      -> samples
          -> sample_labels / sample_attributes
```

建议的导出记录至少保存来源病例样本 ID、数据集样本 ID、脱敏版本、导出时间、操作者、内容哈希和导出规则。标注应针对数据集样本或其切片/区域对象保存，不能把临床病例中的临时分析数值直接当作训练标签。

模型预测结果应关联到 `samples` 或未来的推理任务对象，同时保留原始病例样本 ID、模型版本、输入哈希、参数、结果文件和时间。这样可以从预测回溯到脱敏数据集，再回到授权范围内的原始病例。

数据集版本应冻结样本清单、标签版本、划分和输入哈希。训练、验证和测试划分应以患者或病例为单位进行分组，不能只按图片随机切分；同一病例、同一原图的裁剪图、增强图和重复导入不能跨集合出现。导出前应执行重复哈希、来源病例分组和近重复图像检查。

这部分涉及新表和新的隐私边界，实施前必须单独创建并批准 OpenSpec Change。

## 7. 建议实施顺序和验收标准

1. **先确定安全边界**：确认单机 Electron 模式还是多用户内网模式，确认是否需要登录和病例级授权。验收：形成批准的权限矩阵和静态文件访问策略。
2. **修复上传一致性**：唯一对象名、格式验证、失败清理和删除重试。验收：成功、失败、重复、并发、删除失败测试通过，数据库和文件扫描结果一致。
3. **增加访问控制**：登录、角色、病例权限和受保护下载接口。验收：未登录、无权限、管理员和操作员场景均有自动测试。
4. **分组处理依赖漏洞**：先生产依赖，再开发依赖。验收：锁文件可重复安装，测试、构建和审计结果有记录。
5. **治理 lint 和状态同步**：先 Hook，再类型，最后规范。验收：lint 通过，病例/样本/报告/分析切换回归通过。
6. **设计病例到数据集的导出链路**：先建模和脱敏规则，再决定 Schema。验收：能够追溯来源、冻结版本并证明没有病例级数据泄漏。

## 8. 待确认设计决策

- 系统当前是否只允许单机单用户使用，还是需要支持多用户内网访问。
- 是否必须保留原始图片在线预览，还是使用受保护的临时下载链接。
- 上传失败后的清理策略采用请求内补偿，还是引入文件对象状态和后台清理任务。
- 图片允许的格式、尺寸、像素数量和总容量上限。
- 是否接受新增用户、会话、权限和文件对象相关数据库表。
- 训练数据是否必须从病例导出，以及病例脱敏和授权由谁审批。
- 依赖修复是否允许升级 Express 主版本或 `uuid` 到 14.x。
- lint 修复是否允许调整分析面板的演示数据和统计逻辑，还是只做类型和依赖数组修正。
